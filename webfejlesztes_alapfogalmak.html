1. Kliens-szerver modell (client-server)

Minden weboldal működésének alapja: a kliens (böngésző) kéréseket küld, a szerver (a háttérben futó program) ezeket feldolgozza, és választ (adatot, HTML-t, JSON-t) küld vissza.
A frontend a kliens oldalán fut (amit a felhasználó lát: HTML, CSS, JS a böngészőben), a backend a szerveren fut (adatfeldolgozás, adatbázis-kezelés, üzleti logika).

2. Weboldal felépítése (frontend rétegek)

Egy weboldal háromféle technológiát kombinál: a HTML adja a tartalmat és szerkezetet, a CSS a kinézetet (stílust), a JavaScript pedig az interaktivitást (dinamikus viselkedést).
RétegFeladataPélda
HTMLStruktúra, tartalom<h1>, <p>, <div>
CSSMegjelenés, elrendezésszínek, betűtípus, flexbox/grid
JavaScriptViselkedés, interakciógombra kattintás, form validáció, API hívás
Egyszerű JS API-hívás a böngészőből (frontend)
fetch("/api/felhasznalok")
  .then(response => response.json())
  .then(data => console.log(data));

3. Node.js és a szerver oldal

A Node.js egy futtatókörnyezet, amivel JavaScriptet nem csak a böngészőben, hanem szerver oldalon is futtathatunk. Ezzel írhatunk olyan programot, ami fogadja a kliens kéréseit, adatbázissal kommunikál, és választ küld vissza.
Egyszerű Node.js szerver (Express keretrendszerrel)
const express = require("express");
const app = express();

app.get("/api/felhasznalok", (req, res) => {
    res.json([{ id: 1, nev: "Anna" }]);
});

app.listen(3000, () => {
    console.log("A szerver fut a 3000-es porton");
});
Express a legelterjedtebb Node.js keretrendszer (framework), ami leegyszerűsíti az útvonalak (route-ok), middleware-ek és API-k kezelését.

4. API és kérés-válasz kapcsolat

Az API (Application Programming Interface) egy "szabályrendszer", amivel a frontend és a backend (vagy két különböző rendszer) kommunikálhat egymással. A leggyakoribb típus a REST API, amely HTTP metódusokat használ.
HTTP metódusMire való
GETAdat lekérdezése
POSTÚj adat létrehozása
PUT / PATCHMeglévő adat módosítása
DELETEAdat törlése
Példa: CRUD végpontok Express-ben
app.get("/api/termekek", getOsszesTermek);      // lekérdezés
app.post("/api/termekek", ujTermekLetrehozasa);  // létrehozás
app.put("/api/termekek/:id", termekModositas);   // módosítás
app.delete("/api/termekek/:id", termekTorles);   // törlés

5. Adatbázis-kapcsolat

A backend jellemzően egy adatbázishoz (pl. MySQL, PostgreSQL, MongoDB) csatlakozik, hogy tartósan tárolja és lekérdezze az adatokat. A kapcsolathoz kapcsolati adatokra (host, felhasználónév, jelszó, adatbázisnév) van szükség — ezeket soha nem írjuk a kódba közvetlenül, hanem .env fájlban tároljuk (lásd 11. pont).
Adatbázis-kapcsolat Node.js-ben (MongoDB példa)
const mongoose = require("mongoose");

mongoose.connect(process.env.DATABASE_URL)
  .then(() => console.log("Adatbázis kapcsolódva"))
  .catch(err => console.error("Kapcsolódási hiba:", err));

6. Wireframe

A wireframe egy egyszerű, "drótváz"-szerű vázlat egy weboldal vagy alkalmazás elrendezéséről, még mielőtt a tényleges design vagy kódolás elkezdődne. Célja, hogy gyorsan megtervezzük, mi hova kerül (fejléc, navigáció, tartalom, lábléc), design elemek (színek, betűtípus) nélkül.
Wireframe-eket gyakran olyan eszközökkel készítenek, mint a Figma, Balsamiq vagy akár papír-ceruza.

7. ER modell (Entity-Relationship diagram)

Az ER-modell azt mutatja be, hogyan épül fel az adatbázis: milyen entitások (táblák, pl. Felhasználó, Rendelés) vannak, milyen attribútumaik (mezőik) vannak, és milyen kapcsolatban állnak egymással (pl. egy felhasználónak több rendelése lehet).
PK = elsődleges kulcs (Primary Key, egyedi azonosító), FK = idegen kulcs (Foreign Key, egy másik táblára mutat).

8. UML modell

Az UML (Unified Modeling Language) egy szabványos vizuális nyelv a szoftver felépítésének leírására. Legelterjedtebb formája az osztálydiagram (class diagram), amely az OOP osztályokat, azok tulajdonságait, metódusait, és a köztük lévő kapcsolatokat (öröklődés, asszociáció) mutatja.
A háromszög nyíl az öröklődést jelöli: az Admin és a Vasarlo osztály is a Felhasznalo osztályból származik.

9. Git és GitHub

A Git egy verziókezelő rendszer, amivel nyomon követhetjük a kód változásait az idő során, és több fejlesztő is dolgozhat egyszerre ugyanazon a projekten. A GitHub egy felhő alapú platform, ahol a Git-repókat (repository = tárolót) tároljuk, megosztjuk és együttműködünk rajtuk.
FogalomJelentés

CommitEgy "mentési pont" a kód állapotáról, üzenettel
BranchElágazás, amin önállóan lehet fejleszteni a fő kód érintése nélkül
Pull Request (PR)Kérés, hogy egy branch változásait beolvasszák a fő ágba

git add .                      # változások jelölése
git commit -m "Bejelentkezés hozzáadva"

10. Trello / projektmenedzsment (Kanban)

A Trello egy Kanban-alapú projektmenedzsment eszköz, ahol táblákon (board) belül listákkal (pl. "Teendő", "Folyamatban", "Kész") és kártyákkal (card = egy-egy feladat) szervezzük a munkát. Célja, hogy vizuálisan lássuk, hol tart a csapat/projekt.

11. .env fájl (környezeti változók)

Az .env fájl olyan érzékeny vagy környezetfüggő adatokat tárol (jelszavak, API kulcsok, adatbázis-elérési útvonalak, portszámok), amelyeket nem szabad közvetlenül a kódba írni vagy GitHub-ra feltölteni. A kód ezekhez az értékekhez a process.env objektumon keresztül fér hozzá.
.env fájl példa
PORT=3000
DATABASE_URL=mongodb://localhost:27017/projektAdatbazis
JWT_SECRET=titkos_kulcs_ide
API_KEY=abc123xyz
Használata Node.js-ben (dotenv csomaggal)
require("dotenv").config();

const port = process.env.PORT;
const dbUrl = process.env.DATABASE_URL;
Fontos: az .env fájlt mindig fel kell venni a .gitignore fájlba, hogy véletlenül se kerüljön fel GitHub-ra! Helyette egy .env.example fájlt szokás megosztani, ami csak a kulcsneveket tartalmazza, értékek nélkül.

12. Jó backend logika alapelvei

A backend nem csak "működnie" kell — átláthatónak, karbantarthatónak és biztonságosnak is kell lennie. Ehhez néhány bevált elvet érdemes követni.
1
Rétegekre bontás (separation of concerns): ne írj mindent egy fájlba. Külön legyen a route (útvonal), a controller (a kérés feldolgozása), a service (üzleti logika) és a model (adatstruktúra/adatbázis-elérés) réteg.
2
Validáció: minden bejövő adatot ellenőrizni kell (típus, kötelező mezők, formátum), mielőtt feldolgoznánk vagy elmentenénk — soha ne bízz meg vakon a kliens oldali adatban.
3
Hibakezelés: minden aszinkron művelet (adatbázis-hívás, API-hívás) legyen try/catch-be csomagolva, és a hibákról érthető, de nem túl részletes választ küldjön a szerver (ne szivárogtass belső hibaüzeneteket a felhasználónak).
4
Biztonság: jelszavakat soha ne tárolj titkosítatlanul (hashelés, pl. bcrypt), használj környezeti változókat a titkos kulcsokhoz, védd az API végpontokat hitelesítéssel (authentication) és jogosultságkezeléssel (authorization).
5
Egyértelmű API-válaszok: konzisztens formátumban (pl. mindig { success, data, error } struktúrában) és megfelelő HTTP státuszkódokkal (200, 201, 400, 404, 500) válaszolj.
6
Ne ismételd magad (DRY elv): ismétlődő logikát (pl. hitelesítés-ellenőrzés) szervezz middleware-ekbe vagy segédfüggvényekbe, hogy ne kelljen minden route-ban újraírni.
Réteges felépítés példa (route → controller → service → model)
// routes/felhasznalo.js
router.post("/regisztracio", felhasznaloController.regisztral);

// controllers/felhasznaloController.js
async function regisztral(req, res) {
    try {
        const ujFelhasznalo = await felhasznaloService.letrehoz(req.body);
        res.status(201).json({ success: true, data: ujFelhasznalo });
    } catch (err) {
        res.status(400).json({ success: false, error: err.message });
    }
}

// services/felhasznaloService.js
async function letrehoz(adatok) {
    validalAdatok(adatok);              // 1. validáció
    const hashelt = await hashJelszo(adatok.jelszo); // 2. biztonság
    return FelhasznaloModel.create({ ...adatok, jelszo: hashelt }); // 3. adatbázis
}

Projekt-felépítési ábra — mi hová kerül

Egy tipikus Node.js/Express backend projekt mappastruktúrája, réteges felépítéssel. Ez mutatja, hogy melyik fájl milyen feladatot lát el, és hogyan kapcsolódnak egymáshoz.
projekt/ ├── node_modules/ # telepített csomagok (nem kerül fel GitHub-ra) ├── public/ # statikus fájlok: képek, CSS, kliens oldali JS │ ├── css/ │ ├── js/ │ └── images/ ├── views/ # ha van szerver oldali renderelés (pl. EJS, Handlebars sablonok) ├── routes/ # útvonalak: melyik URL melyik controllert hívja │ ├── felhasznaloRoutes.js │ └── termekRoutes.js ├── controllers/ # a kérés fogadása, válasz összeállítása │ ├── felhasznaloController.js │ └── termekController.js ├── services/ # üzleti logika (a "mit és hogyan csinálunk") │ └── felhasznaloService.js ├── models/ # adatstruktúrák, adatbázis-sémák (pl. Mongoose modellek) │ ├── Felhasznalo.js │ └── Termek.js ├── middleware/ # pl. hitelesítés-ellenőrzés, hibakezelés, naplózás │ ├── authMiddleware.js │ └── errorHandler.js ├── config/ # beállítások (adatbázis-kapcsolat, konstansok) │ └── db.js ├── .env # titkos környezeti változók — NEM kerül GitHub-ra! ├── .gitignore # mit hagyjon ki a Git a verziókezelésből (pl. node_modules, .env) ├── package.json # projekt adatai, függőségek, futtatási parancsok ├── README.md # projekt leírása, telepítési útmutató └── server.js / app.js # a szerver belépési pontja, itt indul el minden
routes/ — csak azt dönti el, melyik URL-hez melyik controller-függvény tartozik.
controllers/ — fogadja a kérést, meghívja a megfelelő service-t, visszaküldi a választ.
services/ — itt van az üzleti logika: számítások, validáció, döntések.
models/ — leírja az adatbázis tábláinak/kollekcióinak szerkezetét.
middleware/ — minden kérésen "áthalad", mielőtt a controllerhez érne (pl. bejelentkezés-ellenőrzés).
config/ — központi hely a beállításoknak, pl. adatbázis-kapcsolódás.
.env — titkos adatok, sosem kerül fel nyilvános repóba.
server.js — az egész alkalmazás "kiindulópontja", ez indítja el a szervert.
Ez a felépítés (routes → controllers → services → models) biztosítja, hogy a kód átlátható, tesztelhető és könnyen bővíthető maradjon, még akkor is, ha a projekt nagyra nő.
